## Context for this initiative

`Table#createViewModel` rebuilds from scratch on every call, and building a view
model instantiates every plugin. A consumer whose column array is derived — new
array identity per reactive pass, same columns inside — therefore discards all
plugin state on each rebuild: pagination returns to page 1, sort keys are lost,
and (before the fix below) the virtual-scroll container was left bound to a dead
closure.

This was scoped as three tracks. **Track A is already done and committed on
branch `chore/touchups`** — `addVirtualScroll`'s state was hoisted into its
config closure so the action identity, scroll position and measured heights
survive a rebuild (`9963373` red tests, `29b4ec0` implementation). Track A does
not generalize: `addSortBy`, `addTableFilter`, `addGroupBy`,
`addResizedColumns`, `addColumnFilters` and `addSelectedRows` genuinely consume
the per-view-model `columnOptions` / `tableState` argument, so their state
cannot move up a level.

**Tracks B and C are what plan 001 covers**, and they collapse into a single
plan rather than two: Track C's remaining item (C3 — asserting `pageIndex`
survives a rebuild) tests an API that Track B introduces, so it cannot be
executed or verified ahead of it. Splitting them would produce a plan whose
done criteria is "these tests fail," which is an invitation for an executor to
implement the other half unprompted. C1 and C2 — the virtual-scroll rebuild and
remount tests — already landed with Track A.

## Dependency notes

- 001 depends on nothing in this batch. It does assume the Track A fix at
  `29b4ec0` is present, because one of its STOP conditions is unexpected
  failures in `addVirtualScroll.test.ts`.
- Reuse and the Track A hoist are complementary, not redundant. Reuse preserves
  state when the caller can promise the columns are unchanged; the hoist
  preserves the DOM binding even when it can't, because a genuine column change
  still rebuilds and still re-runs no action.

## Findings considered and rejected

- **Automatic structural signature instead of an explicit `reuseKey`.** The
  original sketch was to hash the columns — flat ids plus an accessor/header
  signature — and reuse on a match, which would need no consumer change at all.
  Rejected: headers can be renderer components and accessors are frequently
  inline arrows, so any identity-based signature misses on exactly the derived-
  column-array callers it is meant to serve, and any deeper comparison over
  closures and components is unsound. An explicit key is a smaller win — it
  demotes a consumer-side column-comparison guard to a key expression rather
  than deleting it — but it is honest about who is making the promise.
- **Hoisting state in the remaining stateful plugins, Track-A style.** Rejected
  as a general fix: six of them consume their per-view-model init argument, so
  it is a real per-plugin refactor each, not the mechanical indentation change
  it was for `addVirtualScroll`. Reuse at the `Table` level covers all of them
  at once.
- **A keyed map instead of a single cache slot.** Rejected: it would pin plugin
  instances for every key ever seen for the life of the `Table`. The cost is
  that alternating between two keys rebuilds every time; that is a silent loss
  of benefit rather than a correctness bug, and it is recorded in 001's
  maintenance notes.
